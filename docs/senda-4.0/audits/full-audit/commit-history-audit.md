## Issue introduction, attempted fixes and current disposition

### 1. Biller authentication and tenant boundary

- **Introduced:** `1e4b55d…` M1 scaffold created the Biller auth/session implementation.
- **Subsequent commits:** M4 (`7fbdda5…`) added partner API key auth but did not change Biller cookie encoding; M5 (`2561237…`) added Biller-session-gated proof download and dashboard access; M6 did not repair the session.
- **Current behavior:** session claims (`userId`, `institutionId`, `email`) are Base64URL JSON without signature/server lookup/expiry; the `BILLER_SESSION_SECRET` env example is unused; password stub is stored/compared as plaintext. `HttpOnly` does not make the cookie tamper-proof.
- **Fix/reintroduction:** no fix or reintroduction found in any branch/commit. Treat all tenant-scoped Biller data/proof endpoints as unfit for real tenants until signed/server-side sessions, password hashing, expiry/revocation, secure cookie options and authorization tests exist.

### 2. Retry key isolation and concurrency

- **Introduced:** M1 (`1e4b55d…`) with globally unique `Attempt.idempotencyKey` and global lookup/replay.
- **Changed:** M4 (`7fbdda5…`) formalized partner `retry_key` aliases and replay/conflict responses; it still did not compare the existing attempt's `partnerId` to the calling partner.
- **Attempted fix:** `941f3c1…` fixed the reported concurrent duplicate-key 500 by reloading and replaying the winning attempt.
- **Residual:** both the initial lookup and race reload remain key-only; the replay comparison checks link, obligation and amount but not partner. A retry key used by another partner can return the existing instruction if that caller supplies the same tuple. Global uniqueness compounds the cross-partner isolation flaw. No later commit fixes or reintroduces it; the flaw persists at HEAD.

### 2a. Multiple active attempts for one obligation

- **Introduced:** M1 instruction/validation flow.
- **Current behavior:** `validatePayment` treats both `open` and `instructed` obligations as payable. `instructPayment` performs validation before its transaction and records no one-active-attempt constraint. A second request with a different retry key can therefore create another instruction against an already-instructed obligation; concurrent distinct keys can race similarly.
- **Fix/reintroduction:** none found in history. Open PR #15 explicitly recommends a one-open-attempt rule, but the code and current scenario pack do not enforce/test it. Treat as a duplicate-settlement/integrity risk; define transitions and enforce them atomically with an appropriate DB constraint/transaction strategy.

### 3. Meaning and provenance of “proof”

- **Introduced:** M1 confirmation code creates `proven` plus `senda.proof.v1` when reference, amount and currency match a partner-supplied confirmation; local JSON is written before DB transaction completion.
- **Documentation/UI changes:** M4 documents mismatch handling; PR #7 research explicitly says partner attestation is not school receipt; PR #10 changes visible status to “Confirmed”; dogfood/pilot screens disclose test/sandbox status in some places.
- **Residual:** a matching partner statement is not independent bank-credit or biller-allocation evidence. “Confirmed”/“payment proof” can still imply stronger evidence than the system has. Local filesystem writes inside the database transaction can orphan files and are unsuitable for ephemeral/multi-instance deployments.
- **Fix/reintroduction:** no durable storage/outbox, independent credit verification, lifecycle split or display-level provenance enforcement was found.

### 4. Public pilot/demo endpoints and exposed sandbox key

- **Introduced:** `9f2b329…` M6 adds `GET /api/v1/pilot/handoff` with an `attempt_id` lookup and no authentication; returns beneficiary/student reference, obligation/payment information, partner, and proof metadata. The pilot page sends the full sandbox key to a client component.
- **Related prior surface:** M1 added the unauthenticated demo dogfood route, which performs mutations and a synthetic confirmation using the seeded fixture partner.
- **Fix/reintroduction:** no route auth or production-mode guard found. These are demo glue, not supported production APIs; if deployed or configured with a non-demo key they create disclosure, integrity and credential-exposure risks.

### 5. Script retry default

- **Introduced:** M6's script defaults every path to Ada/`obl_001`, so running a successful happy path first consumes that obligation and a subsequent mismatch run can fail as “not open.”
- **Fixed:** `b45578a…` selects Ben/`obl_002` by default for mismatch and updates the runbook; still requires an open bill. This is the only explicit behavioral fix to a previously reported operational issue in the post-M1 app changes reviewed here.

### 6. Other scope findings carried through history

- M1 established the school-specific `SchoolUser`, `Beneficiary.studentRef`, `grade`, fee-template and obligation vocabulary; subsequent language edits are display aliases, not schema generalization.
- M1 proof artifact storage and destructive seed remain prototype-only; no later history replaces local storage or adds a production guard for the seed script.
- M1/Connect validation accepts an already-instructed obligation and lacks a one-active-attempt rule; this enables repeat/double instructions under distinct retry keys. Open PR #15 recognizes the risk as a proposed policy but does not implement it.
- M4 added partner-key auth and retry semantics, but no full unit/integration suite, rate limiting, signed callbacks, partner credential lifecycle or authorization test harness was added.
- Research, lock and fixture changes are additive documentation/policy history; they do not establish live partner willingness, payment volume, bank credit, local legal status or school receipt.
