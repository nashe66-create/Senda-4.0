# Senda 4.0 code audit

**Baseline:** `4bf9ed5dbe46e454baaa176f0c62df634230e173`  
**Audit date:** 23 November 2026  
**Scope:** All 44 tracked files under `apps/web`, root `README.md`, `.gitignore`, and `docker-compose.yml`; Prisma schema, migration, seed and dependency manifests; existing audit documents. The audit was read-only with respect to application code, schema, migrations, branches and PRs. Runtime evidence and commands are in [runtime-and-test-results.md](runtime-and-test-results.md); security findings and acceptance criteria are in [security-findings.md](security-findings.md).

## Executive assessment

The checked-in web application is a Next.js/TypeScript/PostgreSQL/Prisma **prototype and guided sandbox**, not a production-ready payments or biller platform. The build, lint, typecheck, Prisma validation and isolated migration completed successfully after setup. Manual API checks demonstrated significant authentication, tenant-isolation and payment-integrity weaknesses. Do not connect real partners, billers, credentials, personal data or settlement flows until the P1 findings in the security report are resolved and independently tested.

The repo has 88 tracked files total and 44 under `apps/web`; 36 app files are source/configuration/text manifests. Static SVG/favicon assets are not executable code. The app has seven API route files and no `middleware.ts`, test script, or tracked app test files. The existing inventory/history and research audits provide the broader doc, branch, PR and business context; they do not substitute for the runtime checks recorded here.

## Implemented behavior versus simulation

| Area | Evidence-based status |
|---|---|
| Partner authentication | Connect validate/instruct/confirm require an active partner record whose stored SHA-256 API-key hash matches (`src/lib/auth.ts:6-8,20-60`; route handlers under `src/app/api/v1/connect/`). |
| Validate | Checks an active link, ZW corridor, institution live/KYB flags, link/beneficiary/obligation association, obligation status and freshness, amount, eligible/verified destination, partner country and destination capabilities (`src/lib/connect.ts:111-288`). |
| Instruct | Creates attempt and frozen payout instructions in a Prisma transaction and changes obligation status (`src/lib/connect.ts:397-454`). The retry mechanism handles matching retries but is global across partners and does not prevent a second active attempt under a different retry key. Both behaviors were reproduced locally. |
| Confirm/reconciliation | Compares the supplied payment reference, amount and currency against the instruction. A match sets the attempt and obligation to `proven` and creates a proof record; a mismatch sets `needs_reconcile` and creates no proof (`src/lib/connect.ts:526-748`). This is **partner-submitted attestation**, not a bank, wallet, recipient-credit or school-allocation feed. |
| Proof storage | A local JSON file plus a database JSON payload; not S3/R2, and the filesystem write occurs before the database transaction commits (`src/lib/proofs.ts:9-21`; `src/lib/connect.ts:659-740`). |
| Biller | Server-rendered, read-only view over seeded institution/beneficiary/obligation/attempt data; proof downloads are tenant-filtered using the Biller cookie (`src/app/biller/page.tsx:19-107`; `src/app/api/v1/biller/proofs/[attemptId]/route.ts:17-33`). The page explicitly describes sandbox attestation, not a live webhook or bank feed. |
| Dogfood | An unauthenticated route looks up the seeded partner, performs validate/instruct, then writes a synthetic happy/mismatch confirmation and may issue a proof (`src/app/api/v1/dogfood/run/route.ts:13-18,28-83`). This is simulation, not a payment test against a real rail. |
| Pilot handoff | An unauthenticated attempt-ID lookup returns institution, beneficiary/student reference, bill, partner, confirmation and proof metadata (`src/app/api/v1/pilot/handoff/route.ts:11-98`). |

## Confirmed code and runtime findings

1. **Unsigned Biller session and ineffective tenant boundary — High (P1).** `src/lib/auth.ts:65-96` Base64URL-decodes JSON and trusts `userId`, `institutionId` and `email`; it never verifies a signature or server-side session. Login sets an HttpOnly/Lax cookie, but no integrity protection (`src/app/api/v1/biller/login/route.ts:20-47`). The configured `BILLER_SESSION_SECRET` appears only in `.env.example:8`; it is not consumed by auth code. In an isolated runtime, a hand-crafted cookie made `/biller` and an organisation-scoped proof download return HTTP 200. See SF-01.
2. **Multiple active instructions for one obligation — High (P1).** Validation explicitly accepts both `open` and `instructed` (`src/lib/connect.ts:192-195`), and the transaction creates another attempt for a new key (`397-454`). After the first request changes status to `instructed`, a second request for the same bill with a different retry key returned HTTP 200 and a different attempt ID. See SF-02.
3. **Cross-partner retry-key replay — High (P1).** `loadAttemptByRetryKey` queries only the globally unique key (`src/lib/connect.ts:372-400`; schema `prisma/schema.prisma:236`; migration `migration.sql:256`). Replay comparison checks bill/link/amount but not partner (`connect.ts:328-369`). A second seeded partner credential replayed the first partner's request and received the same attempt ID and customer reference (HTTP 200). See SF-03.
4. **Demo partner key sent to the browser — High (P1) if the configured key has real authority.** `/pilot` passes `SANDBOX_API_KEY` (or its fallback) as a client prop (`src/app/pilot/page.tsx:6-12,100`), and the client stores and sends it in the Authorization header (`pilot-client.tsx:79,101`). The rendered pilot response contained the configured test key. The seed also has fixed demo-key fallbacks (`prisma/seed.ts:34-41`). Never configure this value with a production or reusable partner credential. See SF-04.
5. **Unauthenticated demo mutation — High (P1) outside an isolated demo.** `POST /api/v1/dogfood/run` has no authentication or environment guard; it obtains the seeded partner directly and can create instructions, synthetic confirmations and proofs (`src/app/api/v1/dogfood/run/route.ts:28-83`). An unauthenticated local request returned HTTP 200 and `proof_issued: true`. See SF-05.
6. **Unauthenticated handoff discloses payment and student-linked data — High (P1) with real records.** `GET /api/v1/pilot/handoff` has no authentication/tenant check, and the attempt ID is the sole selector (`route.ts:11-31`). An unauthenticated local call returned HTTP 200 with organisation, beneficiary, student-reference, payment-reference and proof-metadata sections. See SF-06.
7. **“Proven”/“payment proof” can overstate partner attestation — High (P1) before real-money use.** A match of partner-supplied reference, amount and currency is sufficient to create `senda.proof.v1` and set `proven` (`src/lib/connect.ts:526-527,632-743`). The proof includes a source field, but the Biller label renders `proven` as “Confirmed” (`src/lib/ui-labels.ts:8-13`), while there is no independent credit/allocation evidence. See SF-07.
8. **Seed is destructive and has no production guard — High (P1) if pointed at a non-fixture database.** `prisma/seed.ts:20-31` deletes every row from the domain tables before recreating fixtures. The isolated audit database was the only target used. See SF-08.
9. **Local proof files are not durable and can orphan — Medium (P2).** `src/lib/proofs.ts:9-21` writes to local disk. The caller does this inside a database transaction before commit (`connect.ts:659-740`), so a later DB failure can leave a file; ephemeral/multi-instance deployments cannot rely on this storage. See SF-09.
10. **Development Compose exposes a known-password database port — Medium (P2) if used on a reachable host.** Root `docker-compose.yml:4-17` publishes port 5432 without a loopback-only host binding and uses fixed development credentials. It is local-dev configuration, not production configuration. The audit did not start Compose or connect to its database. See SF-10.

## Additional correctness and completeness gaps

- The confirm route accepts `settled_at` as an unconstrained string (`src/app/api/v1/connect/confirm/route.ts:32-40`); `connect.ts:655-657` constructs a `Date` without an explicit validity check. Invalid input can fail at database persistence rather than return a clear validation response.
- `confirmPayment` requires an attempt and instruction and checks partner ownership, but no explicit allowed attempt-state check is visible before a first confirmation (`src/lib/connect.ts:539-574`). A valid state-machine policy and regression cases are needed before introducing cancellation/reversal/ops workflows.
- No app-level rate limiter was found in the tracked routes/config; a hosting proxy could provide one, but that is not evidenced here. Login, partner endpoints and the public dogfood route should have documented limits and abuse monitoring before public deployment.
- The seed stores the demo password as plaintext `password_stub` and compares it directly (`prisma/schema.prisma:121`; `prisma/seed.ts:88-91`; login route `:20`). This is marked as a stub but is not a suitable credential design for real users.
- `npm test` cannot run because `apps/web/package.json` has no test script. The structured 95-case YAML pack validates successfully but is a scenario specification/pack validator, not executable API or concurrency coverage.
- `npm audit --omit=dev --audit-level=low` reported 6 dependency vulnerabilities: 1 moderate and 5 high, including transitive Prisma/Next.js/PostCSS advisory paths. The exact result is recorded in `runtime-and-test-results.md`; fixes require coordinated dependency upgrades and retesting rather than an unreviewed forced major upgrade.

## Recommended release gate

Before any real partner or biller data: fix SF-01 through SF-08; distinguish partner attestation from independent credit/allocation in status, proof schema and UI; establish durable proof storage; enforce production-safe environment/configuration and seed guards; add executable PostgreSQL/API tests covering tenant boundaries, retry ownership, duplicate/concurrent instructions, confirmation state transitions and proof authorization; then obtain external legal, privacy and settlement-path validation. This report does not recommend application changes as part of the audit.
